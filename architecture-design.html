SARMAAN LC Dashboard — End-to-End Architecture

eHealth Africa · Kano AMR Programme
Summary. The SARMAAN LGA Coordinator Dashboard is a zero-infrastructure, fully static system with no application server and no database. An hourly GitHub Actions workflow (.github/workflows/fetch-data.yml) runs a single dependency-free Python 3 script (fetch_data.py) that pulls every submission from a KoboToolbox survey asset over its REST API, normalises and flattens each record, and overwrites a single JSON file (data.json) at the repository root. That commit is pushed straight back to main by the `github-actions[bot]` identity, which both updates the dataset and serves as the system's audit trail. GitHub Pages serves the static files directly from the repo; two plain HTML pages (index.html, insights.html) fetch data.json client-side, and all filtering, aggregation, and chart rendering (via Chart.js 4.4.1 from a CDN, plus hand-rolled bar/table widgets) happens in the browser with vanilla JavaScript — there is no build step, framework, or bundler anywhere in the stack.

1Data Sources

The single upstream source of truth is a KoboToolbox survey form filled out daily by LGA Coordinators (LCs) in the field. The form uses a grp_authed/ group prefix on most fields, plus nested repeat groups for device issues, DC roster entries and security incidents.

  • Asset UID akucQN6di4hAxuVEZCku4Z hosted at https://kf.kobotoolbox.org (public multi-tenant Kobo server) — see ASSET_UID / KOBO_BASE constants at the top of fetch_data.py (lines 10–11).
  • Raw submission fields consumed include today, grp_exercise/report_date, auth_lc_lgalabel, auth_lc_name, grp_geofence/result, grp_geofence/distance_loc_lga, grp_authed/activity_type (space-delimited multi-select codes such as dct, field, sup, mon, stk, tmg, esc, transit), plus repeat-group arrays grp_authed/grp_devices/device_issues and roster/security sub-fields — all referenced inside clean(row) in fetch_data.py (lines 81–158).
Evidence: fetch_data.py:10-11, 76-158

2Ingestion

Ingestion is a scheduled pull, not a push/webhook. It is implemented as a single GitHub Actions workflow with no external CI system:

  • workflow .github/workflows/fetch-data.yml triggers on schedule: cron '0 * * * *' (hourly, UTC) and on manual workflow_dispatch. It runs on ubuntu-latest, checks out the repo (actions/checkout@v4), executes python3 fetch_data.py with KOBO_TOKEN injected from the repository secret of the same name, then commits and pushes data.json only if it changed (git diff --cached --quiet || git commit ...).
  • script fetch_data.py is stdlib-only Python 3 (urllib.request, json, datetime — no requests, no third-party packages, and correspondingly no requirements.txt in the repo). fetch_all_submissions() pages through /api/v2/assets/<uid>/data/?format=json&limit=500, following the Kobo API's next cursor until exhausted (lines 25–32).
  • Auth uses a bearer-style Kobo token header: Authorization: Token <KOBO_TOKEN> (line 20). The token is never written to disk or to data.json.
Evidence: .github/workflows/fetch-data.yml, fetch_data.py:6-32

3Storage

There is no database of any kind (no Postgres/MySQL/SQLite/NoSQL). Persistent state is a single flat JSON file, version-controlled by Git itself:

  • data.json at the repo root — the canonical, currently-served dataset, rewritten by every successful workflow run. Observed shape at time of inspection: {"fetched_at": "...", "total": 742, "rows": [...]}, ~415 KB for 742 rows.
  • public/data.json — a static placeholder ({"fetched_at":"loading...","total":0,"rows":[]}) kept only for the legacy public/index.html; the README explicitly flags the root-vs-public/ ambiguity in GitHub Pages source configuration (README "Note on public/ vs repo root").
  • Git history itself doubles as an audit log/time-series store — every hourly refresh that changes data produces a commit authored by github-actions[bot], so any past state of the dashboard can be reconstructed from commit history on main.
Evidence: data.json (742 rows observed), public/data.json, README.md ("Repository layout" / "Note on public/ vs repo root")

4Transformation / Aggregation

Server-side (build time)

clean(row) in fetch_data.py (lines 81–158) does the heavy normalisation once per hourly run:

  • parse_date() — accepts ISO date strings or Excel/Kobo serial-date numbers and coerces both to YYYY-MM-DD (lines 35–50).
  • g(row, key) — a lookup helper that transparently tries both the grp_authed/-prefixed and unprefixed field name, absorbing schema drift in the Kobo form (lines 76–78).
  • yesno(), safe_int(), safe_float(), safe_str() — type coercion/sanitisation helpers guarding against Kobo's None/nan/em-dash placeholder values (lines 53–74).
  • Multi-select activity_type is split into 8 boolean flags (training, fieldCoord, supervision, dataMonitor, stakeholder, teamMgmt, problemSolving, transit) by testing substring codes (lines 123–130).
  • Nested repeat-group array device_issues is flattened into a device_details list of owner/type/desc/resolved/action objects (lines 144–153).
  • main() filters out rows lacking a usable date or lga, sorts the remainder by (date, lga) for deterministic diffs, and serialises to compact JSON with separators=(",", ":") (lines 161–186).

Client-side (render time)

All further aggregation is re-computed in the browser on every filter change — nothing is pre-aggregated into rollup tables:

  • index.html's inline script: getFiltered() applies the date/status/LGA/activity filters (AND-combined) over the in-memory rows array; renderKPIs, renderDaily, renderActivity, renderCoverage, renderCoords, renderIssues, and renderTable each independently reduce that filtered array (group-by-date, group-by-LGA, sum, count) on every call to apply().
  • insights.html's buildLGAMap(data) builds a richer per-LGA aggregate (submission counts, inside/outside ratio, ward/settlement/household/DC sums, challenge/critical/device/security narrative lists) used by renderHighlights (top/bottom-5 rankings, "inactive since" detection via getYesterdayStr()) and renderLGACards.
  • Shared plumbing (fetch, filter-bar chrome, date multi-select, skeleton/empty/error states) lives once in assets/dashboard.js's Dashboard module, reused by both pages via Dashboard.init({ onData }).

5Application & Service Layer

There is no application server, API layer, or backend process at request time — "the service layer" is entirely the scheduled batch job plus static file serving:

  • Batch/service process: the GitHub Actions runner is the only compute that ever executes on a schedule; it exists only for the duration of fetch_data.py and exits (.github/workflows/fetch-data.yml).
  • Hosting: GitHub Pages serves index.html, insights.html, assets/*, and data.json as plain static files — confirmed by the complete absence of any server framework, Dockerfile, docker-compose file, .env.example, package.json, or requirements.txt in the repository.
  • Shared front-end runtime module: assets/dashboard.js exposes a single global window.Dashboard object (IIFE pattern) providing init(), getRaw(), getSelectedDates(), buildDateList(), and a polling loadData() that re-fetches data.json?t=<timestamp> with cache:'no-store' every 10 minutes (state.refreshIntervalMs, line 24) so an open tab picks up new hourly data without a manual reload.
  • Page-level controllers: the inline <script> blocks at the bottom of index.html and insights.html act as page-specific controllers that plug a render/apply callback into Dashboard.init({ onData }) — effectively a minimal pub/sub between the shared data loader and each page's view logic.
Evidence: assets/dashboard.js:16-25, 250-303, index.html:481-488, insights.html (equivalent boot block), absence of any manifest/infra file confirmed by directory listing

6Output / Presentation

Two HTML pages share one sidebar/layout/theme, driven by a single stylesheet:

  • index.html — "Operations dashboard": KPI strip (7 tiles), a stacked bar chart of daily inside/outside-LGA submissions (Chart.js canvas #cDaily), a horizontal bar breakdown of the 8 activity types, a 4-series line chart of coverage trends (#cCoverage: wards, settlements, DCs, households/10), a ranked coordinator-submission bar list, an issues-flagged panel, and a full per-LGA summary table with a computed TOTAL row.
  • insights.html — "Trend & drill-down insights": a Performance Highlights grid (top/bottom-5 by submissions and households, inside-LGA % ranking, lowest DC coverage, "inactive since" list) explicitly computed over the unfiltered full dataset, a Data Quality Flags section, and a card-per-LGA breakdown across all 44 LGAs.
  • Charting: only the two line/bar canvases use Chart.js 4.4.1, loaded from cdnjs.cloudflare.com/ajax/libs/Chart.js/4.4.1/chart.umd.js with defer; every other "chart" (activity bars, coordinator bars, issue bars) is a hand-built div/width:% bar rendered directly by the page scripts — no charting library involved there.
  • Shared chrome: collapsible sidebar with `localStorage`-persisted collapsed state, a multi-select searchable date dropdown, a mobile filter-toggle button, skeleton loading placeholders (data-skeleton attributes), and an error/empty-state banner — all implemented once in assets/dashboard.css + assets/dashboard.js and inherited by both pages.
  • public/index.html is an older, self-contained single-file version of the same dashboard (inline <style>, inline Chart.js CDN tag, no shared asset files) retained "for reference" per the README, and is not part of the live, currently-maintained data flow.
Evidence: index.html:140-490, insights.html:139-330+, assets/dashboard.css, public/index.html:1-60
