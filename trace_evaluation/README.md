# TRACE Evaluation Toolkit

A portable implementation of the **TRACE Evaluation Framework** (Technical /
Real-world / Adaptive / Outcomes / Economic) — a 5-pillar, weighted rubric
for scoring a complex intervention (an AI agent, a digital health tool, a
policy, or, as applied here, a software product) across its whole
trajectory, not a single-point metric.

This directory is built to be **copied as-is into any other repository**
you need to run a TRACE evaluation on. The engine (`framework/`, `latex/`
preamble, `scripts/`) is completely project-agnostic; the only thing that
changes per project is the data under `assessments/<project_name>/`.

## Directory layout

```
trace_evaluation/
  framework/
    rubric.py      — the 5 pillars, weights, and 15 criteria (data only, never edit per project)
    scorer.py       — validates a project's scores.json and computes the weighted rollup
  scripts/
    generate_figures.py  — renders the pillar/criterion bar charts (matplotlib, eHA palette)
    generate_report.py   — builds the .tex report and compiles it to PDF (pdflatex)
  assessments/
    <project_name>/
      scores.json     — YOU write this: one 0-10 score + a written justification per criterion
      narrative.json  — YOU write this: title-page metadata, executive summary prose,
                         findings/issues/mitigations, limitations, reproducibility notes
      results.json    — generated by scorer.py, do not hand-edit
      report/
        trace_report_<project>.tex  — generated by generate_report.py
        trace_report_<project>.pdf  — the final deliverable
        figures/                    — generated by generate_figures.py
  README.md           — this file
```

## Running an evaluation on a new project

1. **Copy this whole `trace_evaluation/` folder** into the target repo,
   unchanged.

2. **Create `assessments/<project_name>/scores.json`.** One entry per
   criterion key defined in `framework/rubric.py` — run
   `python -c "from trace_evaluation.framework.rubric import TRACE_PILLARS; [print(c.key) for p in TRACE_PILLARS for c in p.criteria]"`
   to list all 15 required keys. Each entry needs:
   ```json
   "system_performance": {
     "score": 7.0,
     "justification": "Cite real evidence — a file, a test count, a commit hash. The scorer rejects any entry with an empty justification."
   }
   ```
   Score against **actual evidence in that project's repo** — commit
   hashes, file:line references, test results, documented (or
   undocumented) gaps. A TRACE score is only as credible as its citations.

3. **Create `assessments/<project_name>/narrative.json`** — title-page
   metadata (repo, branch, commit, evaluator), the Executive Summary
   prose, 3-5 `findings` (strengths), 2-4 `issues` (with a `mitigation`
   each), a handful of `limitations` of the evaluation itself, and the
   `reproducibility` command block. See
   `assessments/travel_analytics_app/narrative.json` for a full worked
   example.

4. **Run the pipeline, from the target repo's root:**
   ```
   python -m trace_evaluation.framework.scorer <project_name>
   python trace_evaluation/scripts/generate_figures.py <project_name>
   python trace_evaluation/scripts/generate_report.py <project_name>
   ```
   The last command writes and compiles the `.tex`/`.pdf` in one step
   (`pdflatex` must be on `PATH` — MiKTeX or TeX Live both work; the
   report is compiled twice so the table of contents resolves).

5. Ship it the same way this evaluation was shipped: a short-lived
   branch, pushed to origin, PR opened for review — see the root
   `README.md`/commit history of this repo for the exact flow used here
   (`feature/trace-evaluation` -> `staging`).

## What never changes per project

- `framework/rubric.py` — the 5 pillars, their weights (20/25/20/25/10),
  and their 15 criteria definitions. If you find yourself wanting to
  reword a criterion per project, don't — reinterpret it in that
  project's `scores.json` justification instead, and note the
  reinterpretation in that project's `narrative.json` limitations (see
  limitation #4 in the worked example). Keeping the rubric itself fixed
  is what makes scores comparable across projects and over time.
- The LaTeX preamble embedded in `generate_report.py` (`build_preamble`)
  — eHA house style, copied from `reports/unit_test_report.tex` in this
  repo. If the house style changes, update it once here and it applies
  to every future project's report.
- `scorer.py`'s validation rules — every criterion must be present, every
  score must be 0-10, every score must carry a non-empty justification.
  This is enforced, not a guideline: a `scores.json` that fails
  validation will not produce a `results.json`.

## What always changes per project

- `assessments/<project_name>/scores.json` and `narrative.json` — the
  entire substance of the evaluation.
- The evaluation target framing (what, exactly, "the intervention" means
  for that project — a whole platform, a single feature, an AI agent's
  behavior on a task) should be decided and stated explicitly in
  `narrative.json`'s executive summary before scoring begins, the same
  way it was agreed for this project before this evaluation started.

## Re-running after fixes

Because `results.json`, the figures, and the `.tex`/`.pdf` are all
generated from `scores.json` + `narrative.json`, re-scoring after acting
on an issue (e.g. adding CI, adding auth) is just: update the relevant
criterion's score and justification in `scores.json`, then re-run the
three commands in step 4. Nothing else needs to change.
